Nav-bar search

The single entry point for both jobs — paste a video link, or search for a movie or show — reachable from the nav bar on every page except search.html, whose own hero already IS the search. On desktop it sits inline in the bar; on mobile it collapses to an icon and expands to take over the bar on tap. It classifies what's typed and branches automatically: once there's something to act on, a compact button appears right in the pill — Download for a detected link, Search for a title query of 2+ characters — so pressing Enter and clicking the button do the same thing. Below: where it lives in the bar at each width, then every state the field itself can be in, then the full sequence for both branches, up to the redirect. What each destination looks like lives in that page's own file, not here.

In the app bar: desktop vs. mobile

Desktop has room for the field inline, next to the doorplate. Mobile doesn't — competing against the doorplate, the live-download chip, and the account avatar in one row, the field loses and collapses to an icon, expanding to take over the bar on tap.

Full flow, start to finish

Both branches start in the exact same nav-bar field — paste a link for a video, or type a title for a movie or show. From there they diverge: a video redirects straight to its own detail page, where the download starts; a title search redirects to the search results page. Nothing downloads, and no results render, inside the field itself.

Captions cite docs/designs/motion.md. Two motions only: spring — the user pressed or dragged something (120ms) — and ease — the system reacting to data or a route (200–380ms). var(--ease) / var(--spring) below are this file's local names for motion.md's --ease-uv / --ease-spring.
